每一条都来自本项目的真实事故，不是泛泛而谈。写代码前过一遍，提交前过一遍检查清单。

## 一、第三方依赖与 SDK

### 1.1 绝不凭记忆写 SDK 调用，先读源码确认签名与阻塞性

**事故**：`dashscope` 的 `SpeechSynthesizer.streaming_complete()` 和
`streaming_cancel()` 都是**阻塞**调用（内部 `complete_event.wait()`）。
凭直觉当成非阻塞写，整个流式播报会退化成同步等待，交互体验直接崩掉。

**做法**：
```powershell
python -c "import inspect; from x import Y; print(inspect.signature(Y.__init__)); print(inspect.getsource(Y.method))"
```
重点确认三件事：**参数签名、是否阻塞、回调在哪个线程触发**。

### 1.2 装了不等于能用；新增依赖必须回归已有能力

**事故**：`resemblyzer` 声明依赖 `webrtcvad`，pip 装完把 `webrtcvad-wheels`
的模块文件覆盖了，而那个版本 `import pkg_resources`——setuptools≥81 已删除。
结果**连原先能用的 VAD 都一起坏了**。pip 显示 "Successfully installed" 时毫无征兆。

**做法**：
- 装完新依赖后，立刻跑一遍**完整测试套件**，不要只看新功能的测试
- 关键模块加 import 冒烟：`python -c "import webrtcvad; webrtcvad.Vad(2)"`
- 遇到版本陷阱要**锁版本并在 requirements 里写清原因**，不要只在自己机器上修好

### 1.3 纯逻辑模块必须可注入依赖

**事故**：上面这些并发、时序、单位 bug 大多**无法用真实硬件复现**。
因为 VAD 检测器、声纹编码器、TTS、播放器都做成可注入，才能用假实现写出
确定性的测试，一次抓出「判定窗口按错单位」这种隐性缺陷。

**做法**：构造函数留一个可选依赖参数，测试传假实现，生产传真实现。

## 二、并发与异步

### 2.1 跑在 `to_thread` 里的代码，取消 asyncio task 是停不住它的

**事故**：`speak()` 跑在 `asyncio.to_thread` 的工作线程里。新一句话到来时
`task.cancel()` 只是取消了 `await`，**线程还在继续往音频流里写**。紧接着
`begin()` 清了打断标志，旧线程更不会退出——新旧两段音频交织进同一个输出流，
听起来就是「两个声音在同时说话」。

**做法**：
- 跨线程的长期任务必须有自己的**退出机制**，不能依赖 asyncio 取消
- 绝不用「清标志位」来作废任务——清标志会让旧任务复活
- 用**单调递增的代号**（generation）作废：新一轮开始就 `generation += 1`，
  旧任务自己发现代号过期就退出

```python
def begin(self) -> None:
    with self._gate:
        self._generation += 1   # 作废所有在播的旧任务
        ...
```

### 2.2 跨线程共享状态一律用锁；等待一律带超时

**事故**：暂停播报若没有兜底超时，一旦判定流程出岔子，播报会**永久卡死**。

**做法**：
- `threading.Condition` / `Event` 管状态，`with` 保证释放
- 所有 `wait()` 都带 timeout，并在超时后主动恢复到一个可用状态
  （见 `speaker.MAX_PAUSE_S` 的处理）

### 2.3 音频回调里只做拷贝和入队

sounddevice 的回调线程里做任何耗时操作都会丢帧。回调只允许 `copy()` +
`put_nowait()`；队列满时**丢最旧的帧**，优先保证低延迟。

### 2.4 事件循环里不许出现阻塞调用

TTS 的 complete/cancel、ASR 的 `stop()`（内部 `join` 工作线程）都是阻塞的。
它们必须经 `asyncio.to_thread` 或专用线程进入，否则整个对话停摆。

## 三、数量、单位与命名

### 3.1 变量名必须带单位，帧和采样点绝不混用

**事故**：声纹判定窗口写成 `int(sample_rate * verify_ms / 1000)` = 960，
但比较对象是**帧数**。600ms 只需要 20 帧，实际要等 960 帧 = 28.8 秒。
声纹功能等于完全没生效，而且没有任何报错。

**做法**：
- 名字写清楚：`verify_frames` / `sample_rate` / `frame_ms` / `verify_ms`
- 换算只在一个地方做，并写注释说明单位
- 这类错误写测试最容易抓：`assert orchestrator._verify_frames == 2`

### 3.2 区分「帧」「块」「字节」「采样点」

音频链路上这四个量反复出现，转换点必须显式且唯一。

### 3.3 时间戳按秒截断时，区间查询右界必须用闭区间

**事故**：周报统计「最近 7 天」，右界用 `created_at < end`。时间戳都按秒截断，
刚讲完一道题就生成周报时，`created_at` 和 `end` 落在同一秒 → 被排除 →
**报告显示「讲题总数 0 道」，今天的题凭空消失**。而且它只在「刚讲完就查」时复现，
平时怎么试都正常。

**做法**：
- 时间窗的右界一律 `<=`，并在代码里注释清楚是闭区间
- 时间相关的代码要有**用真实时钟**（`datetime.now()`）的测试，
  不能用固定时间戳——固定值永远测不出边界同秒的问题
- 同理警惕：分页的 `offset/limit`、浮点相等比较、`>=`/`>` 的取舍

## 四、音频设备（Windows 特有，坑最多）

### 4.1 同一物理设备在多个 host API 下各有一条，能打开与否差别极大

**事故**：蓝牙耳机在 MME / DirectSound / WASAPI / WDM-KS 下各有一条记录。
代码取了「第一个名字匹配」的，正好是 WDM-KS——PortAudio 下**必然**
`Invalid device`。

**做法**：按 `WASAPI > DirectSound > MME > WDM-KS` 排序返回候选列表，
**逐个试开**，全部失败才报错并列出每一项的失败原因。
绝不赌第一个能成（见 `devices.candidate_devices`）。

### 4.2 设备能在列表里看到 ≠ 能打开

配置设备名之前必须试开。提供 `python -m xiaozhi devices --probe` 做这件事。

### 4.3 设备索引不稳定，永远按名字解析，绝不缓存索引

蓝牙设备会动态出现/消失，索引会整体偏移。

### 4.4 PortAudio 只在初始化时枚举一次设备

后连上的耳机不会出现在列表里。启动时必须 `refresh_devices()` 重扫，
并且**必须在打开任何音频流之前**调用。

### 4.5 留意环回设备被当成麦克风

Windows 默认录音设备可能是「立体声混音」，录的是电脑自身声音，
表现是「程序完全听不到你说话」却毫无报错。启动时要检测并告警。

### 4.6 采样率要用设备的真实值

WASAPI 共享模式下不支持的采样率会直接 `Invalid sample rate`。
蓝牙 HFP 端点在 WASAPI 下正好是 16000Hz——整条链路统一 16k 最省事。

## 五、延迟预算与模型加载

### 5.1 任何懒加载都要评估「首次调用」是否落在关键路径上

**事故**：声纹模型（torch）首次加载要 **3.4 秒**。如果等第一次打断判定时
才加载，打断延迟会从 0.2 秒变成 3.4 秒，功能形同报废。

**做法**：落地前先测一次冷启动耗时；凡是可能落在实时路径上的模型，
一律在启动时**预热**（`warmup()`），并把耗时通过状态提示告诉用户。

### 5.2 交互延迟是设计指标，要在代码里体现

打断响应目标 0.2 秒。为达成它，采用「先静音、再验声、错则续播」：
立刻暂停（0.2 秒内），同时收集 0.6 秒语音做身份判定，判定错误就无声续播。
**真打断的响应速度不受判定耗时影响**。

## 六、云端服务对接

### 6.1 云端识别结果不可信，要容错与降级

**事故**：ASR 把「小智」识别成「小志」「这小志」，唤醒词十次有八次不灵。

**做法**：关键词类匹配要内置**同音字变体**且可配置；解析类结果要有
「拿不到就用原文兜底」的降级路径。

### 6.2 判定类功能「拿不准时放行」

声纹比对失败、音频过短、模型异常——一律**判定为本人**。
漏掉一次该有的打断，比拦掉用户一次的打断更让人恼火。

### 6.3 每个云端调用都要有超时和明确的错误信息

失败要能定位到「哪个服务、哪一步、什么原因」，不能只抛 SDK 原始异常。

## 七、可配置性与分层

### 7.1 阈值要独立，不要复用

打断门槛和断句门槛是两件事，共用一个 `min_speech_ms` 会导致调一个坏一个。

### 7.2 `dialogue` 层不依赖任何具体厂商 SDK

只依赖 `asr/base.py`、`tts/base.py`、`vision/base.py` 抽象。
换服务商只改 `cloud.py`，不动业务逻辑。

### 7.3 所有可调参数进 `config/default.yaml`，代码里写默认值

配置项旁必须写清楚**调高/调低分别会发生什么**。

## 八、安全

### 8.1 密钥只放 `.env`，且 `.env` 必须在 `.gitignore` 里

**事故**：在 IDE 里打开 `.env` 会把明文密钥带进对话上下文。

**做法**：
- 不要把 `.env` 打开后截图或分享
- 提交前确认 `.env` 未被 `git add`
- 不要在代码、注释、文档里写任何真实密钥

### 8.2 启动时先校验密钥，再构造客户端

否则空密钥会抛 SDK 层面难以理解的异常，用户不知道要做什么。
报错信息要直接告诉用户「去哪个文件填哪个变量」。

## 十、本项目约定

- **注释用中文，重点写「为什么」**，而不是复述代码在做什么
- 每个模块 docstring 说明它在整体链路里的位置
- 报错信息面向使用者：说清「哪里出了问题」+「你应该做什么」
- 加新功能前先想「这个能不能被假组件测出来」，不能就先改进可测性
